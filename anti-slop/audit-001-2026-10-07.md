## 결론

수정 후보 12개: HIGH 8개, MEDIUM 2개, LOW 2개. 가장 먼저 1번 출처 없는 추천 수치, 3번 가상 정산 동행자, 4번 확대 화면 잘림을 처리하는 것을 권장한다. 제품 소스와 기존 테스트는 수정하지 않았다. AFTER 규칙에 따라 승인한 번호만 수정한다.

## HIGH: 기능·사실성·접근성

### 1. 출처 없는 추천 비율과 인기·월간 추천 표시

규칙: R-17, R-38. `lib/features/home/presentation/home_screen.dart:824`에 방문자 추천 88%, 91%, 94%와 장소명이 고정되어 있으며, 이용자 집계나 기간·출처가 없다. 이 패널은 서버 설정 여부와 관계없이 홈에 나타난다.

추가 근거: `lib/core/l10n/app_language.dart:77`은 "이번 달 로컬 추천"이라고 표시하지만, `lib/features/route_search/data/supabase_route_repository.dart:70`의 조회에는 월간 기간 조건이나 추천 순위가 없고 공개 로그를 발행 최신순으로 반환한다. 홈은 그중 첫 로그를 표시한다.

영향: 사용자에게 검증되지 않은 인기와 기간별 추천 근거를 전달한다.

최소 수정: 집계가 없다면 비율·인기 표현을 제거하고 "지역 둘러보기", "최근 공개 로그"처럼 실제 동작에 맞게 표시한다. 이번 점검에서는 추천 알고리즘 추가를 제안하지 않는다.

### 2. 서버 미설정 상태의 가상 로그가 예시라는 표시 없이 노출됨

규칙: R-17, R-38. `lib/features/route_search/data/route_repository_provider.dart:5`는 서버 미설정 시 MockRouteRepository를 사용한다. `lib/features/route_search/data/mock_route_repository.dart:240` 이후에는 가상 작성자 local.mina, busan.local, hanok.walker와 추천 94%·92%·87%, 다운로드 327·214·148이 들어 있다.

`lib/features/route_search/presentation/widgets/route_card.dart:20`과 상세 화면은 이 값을 실제 추천·작성자 정보와 같은 방식으로 표시한다. UI에서 예시 모드라는 구분이 확인되지 않았다. 서버가 정상 설정된 경우에 대한 지적은 아니다.

최소 수정: 서버 미설정 경로에 명확한 예시 모드 안내를 붙이고 가상 통계는 숨긴다. 개발·테스트용 데이터 자체를 삭제할 필요는 없다.

### 3. 영수증 정산 동행자가 가상 인물 4명으로 고정됨

규칙: R-38, C-5. `lib/features/receipt_settlement/presentation/receipt_settlement_screen.dart:25`는 나·민지·준호·서연을 고정하고, 34행에서 모두 기본 선택한다. 220행과 324행에서 영수증 품목을 이 선택 목록으로 분담하며, 425행에는 참여자 4명이 표시된다.

`ReceiptSettlementScreen`은 travelTitle만 받고 실제 동행자 목록을 받지 않는다. 실제 서버 기반 `TripExpensesScreen`의 동행자 기능과는 별도 경로다.

영향: 실제로 존재하지 않는 동행자가 금액 분담에 포함될 수 있다. 단순 장식 문구보다 우선순위가 높다.

최소 수정: 실제 또는 사용자가 입력한 분담자만 사용한다. 실제 참여자 연결 전이라면 가상 인물이 아닌 "나"만 기본으로 두고 참여자 편집을 제공한다.

### 4. 200% 글씨 확대에서 홈이 넘침

규칙: R-03, C-4. 기존 검사는 1.6배·1.4배까지만 확인한다. 2배 확대한 임시 검사에서 다음을 재현했다.

- 320×720, 글씨 2배: `compact: home`, 오른쪽 45px RenderFlex overflow. 로고와 로그인 버튼이 한 Row에 있고 로고가 유연하게 줄바꿈하지 않는 구조는 `lib/features/home/presentation/home_screen.dart:272`에 있다. 이 경우 예외를 검사에서 회수하여 프레임워크 로그에 발생 위젯 위치는 나오지 않았으므로 이 Row를 원인 후보로 기록한다.
- 844×390, 글씨 2배, 아래로 스크롤: `lib/features/home/presentation/home_screen.dart:851`의 인기 장소 카드 Column에서 아래쪽 62px·27px·62px overflow. 220px 고정 너비와 `88 + textScaler.scale(36)` 높이가 긴 장소명의 두 줄 배치를 담지 못한다.

최소 수정: 헤더가 좁거나 글씨가 커질 때 재배치하고, 장소 카드의 고정 크기를 실제 텍스트 줄 수에 맞게 조정한다. 일반 화면 디자인 전체를 바꿀 필요는 없다.

### 5. 공통 보조 글씨 대비가 일부 배경에서 기준 미달

규칙: R-25. `lib/core/theme/app_colors.dart:19`의 gray500 / textSecondary는 #6B7280이다. 일반 글씨 기준은 4.5:1이다.

- #6B7280 / warmBackground #F7F6F2: 4.4706:1, 미달. 예: `lib/features/trip_planning/presentation/planned_route_log_create_screen.dart:234`의 설명.
- #6B7280 / primaryBlueSoft #DCE5FF: 3.8434:1, 미달. `lib/features/onboarding/presentation/onboarding_screen.dart:101`의 설명은 warmBackground에서 primaryBlueSoft로 이어지는 배경 위에 표시되어 위치별 대비 확인이 필요하다.
- #6B7280 / surfaceMuted #F0EFEA: 4.1990:1, 이 색 조합도 일반 글씨에는 사용할 수 없다. 모든 실제 사용 위치를 검증했다는 의미는 아니다.
- #6B7280 / white: 4.8345:1, 통과. 모든 회색 글씨가 문제인 것은 아니다.

부가 접근성 문제: `lib/core/theme/app_theme.dart:129`의 입력 경계 #E5E7EB와 배경 #FFFEFB는 1.2276:1로 antislop-human의 비문자 3:1 기준에 못 미친다. 경계가 식별 수단인 입력창은 함께 검토한다. 비활성 버튼은 활성 텍스트 대비 위반으로 집계하지 않았다.

최소 수정: 공통 보조 텍스트 토큰을 필요한 만큼 어둡게 하고 입력 경계를 점검한다. 흰색 위에서 통과하는 색을 다른 배경에서도 통과한다고 가정하지 않는다.

### 6. 대표 사진 선택이 키보드로 실행되지 않는 구조

규칙: R-32. `lib/features/trip_planning/presentation/planned_route_log_create_screen.dart:418`의 대표 사진 선택은 GestureDetector.onTap만 사용한다. 바깥 Semantics(button: true)는 설명을 제공하지만 이 선택을 위한 Focus, 키 동작, Semantics.onTap이 없다. 내부 삭제 InkWell은 별도 동작이다.

조건: 계획 루트 발행 화면에서 사진을 추가한 상태. 기본 빈 사진 렌더링 검사에는 나타나지 않는다. 이는 소스 구조로 확인한 결함이며 전체 앱 키보드 실사용 검사를 했다는 의미는 아니다.

최소 수정: 기존 Material 버튼·InkWell 또는 Flutter의 focus/action 기능으로 대표 사진 선택 자체에 키보드 활성화와 포커스 표시를 제공한다.

### 7. 사진 삭제 터치 영역이 약 23×23으로 작음

규칙: R-03, antislop-layoutmobile. 같은 파일의 449~460행은 15px 닫기 아이콘을 사방 4px 패딩으로 감싼 InkWell이다. 부모가 별도 최소 터치 영역을 지정하지 않아 약 23×23이며 스킬의 44×44 기준보다 작다. 접근성 라벨·툴팁도 없다.

조건: 사진을 추가한 후 썸네일 우측 상단 삭제 버튼. 작은 아이콘 자체를 키우라는 지적이 아니라 동작 가능한 영역과 이름의 문제다.

최소 수정: 툴팁이 있는 IconButton 또는 최소 44×44 영역으로 바꾸고, 대표 사진 선택과 삭제의 동작 영역을 구분한다.

### 8. 일부 데이터 화면이 로딩·오류를 빈 상태나 0으로 표시함

규칙: R-27. 아래는 정상적인 빈 결과와 조회 실패·조회 중을 구분하지 않는 구체적인 경로다.

- 홈 `home_screen.dart:96`: 여행 조회 실패를 `_nextPlan = null`로 처리하여 "새 여행 계획 만들기" 상태를 보여준다. 기존 여행 조회 실패를 사용자에게 알리지 않는다.
- 프로필 `profile_screen.dart:280`의 statsSnapshot은 data만 전달하며, 443·450행은 없으면 누적 좋아요·루트 참고를 0으로 표시한다. 집계 조회 실패와 실제 0을 구분하지 않는다.
- 여행 상세 `travel_plan_detail_screen.dart:386`: 동행자 FutureBuilder가 `snapshot.data ?? []`만 사용해 로딩·조회 실패를 빈 목록으로 표시한다.
- 동행자 초대 `trip_invite_screen.dart:46`: `_load()`에 조회 중 상태가 없고 `_busy`는 초대·팔로우·제거에만 사용된다. 검색 결과가 0명일 때의 안내도 없다.
- 초대 코드 `trip_code_screen.dart:31`: 활성 코드 최초 조회의 로딩 상태가 없으며 164행은 목록이 비어 있으면 섹션을 숨긴다. 활성 코드 조회 재시도 성공 시 이전 `_error`를 정리하지 않는다.

최소 수정: 각 기존 조회 상태를 UI에 전달해 로딩, 실제 빈 결과, 실패·재시도를 구분한다. 공통 상태 관리 라이브러리를 추가할 필요는 없다.

## MEDIUM: 목적이 불명확한 시각 요소

### 9. 제목 내용을 반복하는 영문 알약 라벨

규칙: R-09, R-06. `route_search_screen.dart:162`의 FIND YOUR ROUTE는 검색 제목 위의 라임색 pill이며 같은 의미를 반복한다. `home_screen.dart:379`의 NEXT JOURNEY도 여행이 없는 상태에서 "여행을 떠나볼까요?"와 기능적 정보가 겹친다. 디자인 근거 문서에 이 영문 라벨의 목적이 없다.

최소 수정: 두 장식 라벨을 제거하거나 실제 상태 정보로 대체한다. 날짜를 전달하는 D-day 배지와 지역·태그 칩은 의미가 있으므로 함께 제거하지 않는다.

### 10. 여러 화면에 같은 원·링 장식이 반복되고 목적 기록이 없음

규칙: R-01, R-31. `lib/core/widgets/premium_ui.dart:42`의 AppHeroCard는 파란 그라데이션에 `_HeroOrb`, `_HeroRing`을 결합한다. 홈·검색·온보딩에서 같은 모티프가 반복되고 여행 상세·정산에도 orb가 추가된다. 기존 디자인 문서는 색·글꼴·간격을 설명하지만 이 원·링의 제품 의미를 설명하지 않는다.

그라데이션이나 원을 쓰는 것 자체는 위반이 아니다. 사진 업로드의 프레임, 정산의 영수증 선, 여행의 달력 표현은 콘텐츠 연결이 있어 일괄 제거 대상으로 보지 않았다.

최소 수정: 원·링이 방문 동선 같은 브랜드 의미를 갖는다면 소유자가 그 근거를 정한다. 그런 목적이 없다면 해당 장식만 줄인다. 새 디자인 방향이나 자산을 임의로 생성하지 않는다.

## LOW: 문구·브랜드 일관성

### 11. 온보딩 CTA가 다음 행동을 구체적으로 말하지 않음
